## Apps 页：bundleID → App 名称解析
- 重写 `id2name.swift`：原实现用 `Bundle(identifier:)`，对其他 App 永远返回 nil（只能查当前进程已加载的 bundle）。改为调用 bridging header 里已有的 `AppNameForBundleID`（Obj-C helper，走 `LSApplicationProxy +applicationProxyForIdentifier:` → `localizedName`，该属性定义在父类 LSResourceProxy 上，CoreServices/ 头文件可证）。串行队列 + 只缓存命中结果。
- `BQAppListView`：新增 `names`/`requested` State，`.onChange(of: model.items)` 渐进式触发 `resolveNames()`（detached 批量查，一次性回 MainActor 更新）。行布局改为名称为主标题、bundleID 等宽副标题、UUID 第三行；搜索支持名称；按显示名排序。
- `BQRootView` 里 `appName(for: "com.apple.Preferences")` 的既有调用签名不变，且现在能真正解析成功。

## 实测修正：LS 私有 API 被 entitlement 限制
- 真机实测只有 Books/Mail/Messages/Safari 能解析——`applicationProxyForIdentifier:` 对未授权进程只返回少数 Apple 自家 App，第三方 App 返回 nil。
- `id2name.swift` 加文件系统回退：LS miss 后一次性扫 `/var/containers/Bundle/Application/<UUID>/*.app/Info.plist` 和 `/Applications/*.app/Info.plist`，读 `CFBundleDisplayName ?? CFBundleName` 建 bundleID→名称映射。目录列举/文件读取失败时用 `rawBadQuery` 激活一次性 extension（用完立即 `bad_query_release`，避免 200+ 活跃 extension 拖慢 syscall）。映射落盘 `Documents/bundle_name_cache.plist`，避免每次启动重扫。
- 经验：在这台设备（iOS 26+ 目标）上，LS 读操作对侧载 App 不可靠，bad_query 文件系统路线才是通用解。
